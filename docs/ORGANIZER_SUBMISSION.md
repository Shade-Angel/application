# Реализация кейса для организаторов

Executor Balancer — демонстрационная многопоточная система распределения заявок между исполнителями. Она включает интеграционный API внешней АИС, параметризуемый DSL-подбор, транзакционное резервирование, асинхронную доставку назначения, оперативную панель, эмулятор АИС и симулятор потока.

## Что реализовано

| Требование кейса | Реализация в проекте |
|---|---|
| Принимать заявки и изменения исполнителей из АИС | Webhook `POST /ingest/orders`, `POST /ingest/executors`; secret validation, event id idempotency, upsert, входящий API эмулятора АИС |
| Хранить и синхронизировать исполнителей и настройки | AIS emulator CRUD для пользователей и `user_settings`; сериализованные настройки передаются балансировщику и хранятся в `attributes` JSONB; Docker seed создаёт демонстрационный каталог исполнителей |
| Динамически добавлять параметры заявки и исполнителя | Каталог `parameter_definitions` с типом и optional dictionary; значения объектов остаются в JSONB, поэтому новое поле не требует SQL migration; поля каталога становятся доступны в конструкторе правил |
| Настраивать условия подбора | JSON DSL с AND/OR/NOT, типизированными сравнениями, диапазонами, строковыми операциями и операциями по массивам; ссылки на параметры валидируются; UI поддерживает создание фильтра, проверку и dry-run |
| Назначать только активных и подходящих исполнителей | Matching проверяет активность, фильтры, дневной лимит и текущую загрузку, затем выбирает наименьшую оценку среди кандидатов |
| Выполнять параллельную обработку без превышения лимитов | Redis Streams consumer group; несколько workers; SQL `FOR UPDATE` и транзакция при обновлении счётчиков/резервировании; `XACK`/`XAUTOCLAIM` для управления доставкой |
| Учитывать суточные лимиты, веса и квалификацию | Индивидуальный дневной лимит, `null` как unlimited, вес заявки, capacity и квалификация в оценке/attributes; дневная статистика и открытый вес учитываются в выбранной стратегии |
| Обрабатывать дочернюю заявку (`parent_id`) | Вторичная заявка может сохранить исполнителя родительской заявки, если он активен и проходит параметры; для parent executor дневной лимит исключён согласно условию кейса; при недоступности выполняется поиск замены |
| Подтвердить доставку во внешней АИС асинхронно | Transactional outbox → dispatcher → AIS emulator; idempotency key; эмулятор возвращает отдельный webhook подтверждения через случайную задержку 2–10 секунд; ошибки повторяются, затем попадают в DLQ |
| Симулировать заявки и освобождение слотов | Многопоточные сценарии создания заявок, смены статусов, повторного подбора и изменения доступности исполнителей; остановка сценариев из UI |
| Показать KPI, графики и свежие изменения | Dashboard и analytics API для summary/timeline/fairness, живой WebSocket снимок, charts, p50/p95 подтверждения, outbox/stream/DLQ и объяснение выбора |
| Экспортировать аналитику в Excel | `GET /api/analytics/export.xlsx`; листы `Summary`, `Executors`, `Timeline`, `Fairness`, `Assignments`; кнопка доступна из интерфейса |
| Подготовить документацию аналитики и данных | [BPMN](diagrams/BPMN.md) и BPMN 2.0 source, [sequence diagram](diagrams/new-order.md), [ERD обеих PostgreSQL-схем](diagrams/erd.md), [проблемы и альтернативы](PROBLEMS_AND_ALTERNATIVES.md) |

## Архитектура

UI вызывает Balancer API и получает WebSocket-снимки. AIS emulator передаёт новые заявки и изменения исполнителей webhook-ами. API коммитит заявку вместе с stream outbox. Producer публикует событие в Redis Streams; worker выбирает исполнителя и атомарно резервирует лимит вместе с AIS outbox. Dispatcher отправляет назначение в AIS emulator. Подтверждение возвращается отдельным webhook после 2–10 секунд. PostgreSQL — источник истины.

## Что демонстрируется

1. Открыть Overview и показать KPI/графики.
2. Создать демо-заявку, открыть **Explain** и показать, почему выбран исполнитель.
3. Создать условие в конструкторе, проверить DSL и запустить Dry-run.
4. Добавить динамический параметр и справочник, затем использовать их в правиле.
5. Изменить и сохранить режим/веса стратегии.
6. Запустить генератор заявок и сценарий изменения статусов; показать подтверждение АИС и метрики live.
7. Открыть Audit/DLQ, просмотреть историю и при необходимости повторить отправку.
8. Скачать Excel-отчёт и показать листы сводки, исполнителей, timeline, fairness и назначений.

## Итоговая проверка сборки и интерфейса

При последнем Docker smoke-прогоне все сервисы Compose поднялись, `migrate`, `seed`, `sync` завершились с кодом 0; frontend, `/health`, `/ready` возвращали HTTP 200. Вручную в панели проверены навигация, список 60 исполнителей, форма добавления параметра и справочника, валидатор правила, dry-run, сохранение стратегии, генератор заявок, смена статусов и остановка, создание демо-заявки, Explain, Audit/DLQ и кнопка Excel. Backend unit/integration tests и frontend production build указываются отдельно в [LOAD_REPORT.md](LOAD_REPORT.md).

## Честные границы результата

- Цель распределения с отклонением ±1–2% является KPI кейса, а не доказанным результатом этого комплекта: автоматический fairness KPI и алгоритм выбора реализованы, однако чистый изолированный 30-минутный acceptance-прогон на 4000 заявок/час с опубликованным результатом в этой проверке не выполнялся. Не следует представлять целевой коридор как измеренный факт.
- Отдельная таблица для заранее рассчитанных агрегатов указана организаторами как дополнительный плюс. В реализации сводки вычисляются API на основе текущих счетчиков и журналов; отдельной aggregate/materialized таблицы нет.
- Таблица исполнителей в панели служит для просмотра. CRUD исполнителей и их настроек реализован в AIS emulator API; визуальной формы редактирования пользователей нет. Для правил есть toggle/delete в UI; для каталога параметров полноценный edit/delete доступен через REST API, но не через виджеты каталога.
- Acceptance-нагрузка, длительные профили burst, производственные меры доступа/секретов и развертывание на реальном внешнем АИС остаются предметом отдельного окружения и согласованных эксплуатационных требований.
