# Executor Balancer — руководство пользователя

## 1. Назначение

Executor Balancer принимает заявки из внешней АИС и распределяет их между исполнителями с учётом статуса доступности, настроенных правил, открытой нагрузки и дневных лимитов. Назначение сначала резервируется транзакционно, затем передаётся через Redis Streams обработчику и dispatcher. Эмулятор АИС подтверждает или отклоняет назначение с задержкой. События, попытки доставки и ошибки можно просматривать в интерфейсе.

В комплект входят веб-панель, REST API, PostgreSQL, Redis Streams, API-эмулятор АИС, workers, dispatcher, Prometheus и Grafana (опционально). Локальный проект разворачивается через Docker Compose.

## 2. Требования и запуск

Нужны Windows 10/11, Docker Desktop с работающим Docker Engine (режим Linux containers) и свободные порты `5173`, `8000`, `8001`, `5432`, `6379`. Если Docker Desktop просит настроить WSL 2, выполните его инструкции и перезапустите компьютер.

Откройте PowerShell в корне проекта — в этой папке должен быть `docker-compose.yml` — и запустите:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
docker compose up --build -d
docker compose ps
```

Первый запуск занимает несколько минут. Дождитесь статуса `healthy` у `postgres`, `redis`, `api` и `ais-emulator`; фоновые сервисы `worker`, `stream-producer`, `dispatcher` должны быть `Up`. `migrate`, `seed` и `sync` выполняются однократно и штатно завершаются как `Exited (0)`.

Адреса:

- Панель: http://localhost:5173
- API балансировщика / Swagger: http://localhost:8000/docs
- Swagger эмулятора АИС: http://localhost:8001/docs
- Живость API: http://localhost:8000/health
- Готовность API: http://localhost:8000/ready

## 3. Рекомендуемый сценарий демонстрации

1. Откройте панель и убедитесь, что подключение к API активно.
2. На странице **Обзор** посмотрите количество заявок, исполнителей, назначения и метрики распределения.
3. Нажмите **Создать демо-заявку**. Кнопка показывает состояние отправки; после ответа появляется уведомление с номером заявки. Дождитесь, когда в таблице появятся результат распределения и подтверждение АИС.
4. На странице **Заявки** просмотрите статус, назначение и исполнителя. Кнопка **Explain** показывает причину выбора и оценки кандидатов. Список отображает последние записи без поиска и постраничной навигации.
5. На странице **Исполнители** проверьте доступность, нагрузку, дневные лимиты и статистику. Карточка исполнителя показывает параметры, используемые правилами.
6. В **Правилах** создайте условие в визуальном конструкторе. Нажмите **Проверить** для валидации, **Dry-run** для оценки на текущих исполнителях и **Сохранить правило** для включения фильтра в последующие назначения. Правило можно выключить или удалить из списка.
7. В **Параметрах** создайте поля заявки/исполнителя без миграции базы, справочник и его значения. Эти определения используются при построении правил; значения объектов хранятся в их JSONB-атрибутах. Редактирование и удаление записей каталога доступны в API.
8. В **Стратегии** изучите используемые критерии выбора и настройки распределения.
9. На странице **Симулятор** выберите вид активности и нажмите **Запустить заявки**. Счётчики и состояние обновляются во время работы; нажмите **Остановить**, чтобы завершить поток. Здесь также доступны сценарии изменения статусов и доступности исполнителей.
10. В **Аудит / DLQ** изучите результаты и ошибки доставки. Для записей, допускающих повтор, используйте действие повтора и проверьте обновлённый статус.

Полный путь заявки: АИС → проверка webhook → сохранение заявки и outbox → публикация в Redis Stream → worker выбирает и резервирует исполнителя → dispatcher отправляет назначение → АИС возвращает подтверждение → интерфейс обновляет данные. При сбое повторяемые операции остаются видимыми в аудите/DLQ.

Обзор назначения каждого пользовательского раздела находится в [docs/PROJECT_OVERVIEW.md](docs/PROJECT_OVERVIEW.md). Сопоставление функций с требованиями кейса и границы проверки — в [docs/ORGANIZER_SUBMISSION.md](docs/ORGANIZER_SUBMISSION.md).

## 4. Данные и настройки

После запуска `seed` подготавливает демонстрационный каталог АИС и исходные записи, а `sync` синхронизирует 60 исполнителей с балансировщиком. Данные PostgreSQL сохраняются в Docker volume `pgdata` и переживают обычную остановку.

Настройки по умолчанию задаются в `.env.example`. Если нужно менять их, редактируйте локальный `.env` и пересоздайте сервисы командой `docker compose up --build -d`. В частности:

- `API_KEY` — ключ административного API и панели;
- `WEBHOOK_SECRET` — секрет приёма событий АИС;
- `WORKER_CONCURRENCY` — число параллельных задач на worker;
- `REVIEW_STATUS`, `OPEN_STATUSES`, `CLOSED_STATUSES` — семантика статусов;
- `CONFIRM_TIMEOUT`, `MAX_ATTEMPTS` — ожидание подтверждений и число попыток;
- `LIMIT_TZ` — часовой пояс для расчёта дневных лимитов.

Демо-значения секретов годятся только для локальной демонстрации. Перед размещением в общей или внешней среде замените их, ограничьте доступ к портам и настройте подходящую инфраструктуру секретов.

## 5. Проверка и наблюдение

Проверить состояние контейнеров:

```powershell
docker compose ps
```

Посмотреть журналы, например для API и обработки заявок:

```powershell
docker compose logs -f api worker stream-producer dispatcher ais-emulator
```

Остановить вывод логов: `Ctrl+C`. Контейнеры при этом продолжат работать.

Опциональные Prometheus и Grafana запускаются отдельным Compose-профилем:

```powershell
docker compose --profile observability up --build -d
```

Prometheus: http://localhost:9090. Grafana: http://localhost:3000. В локальной конфигурации Grafana использует демонстрационную учётную запись `admin` / `admin`.

## 6. Остановка и сброс данных

Остановить контейнеры, сохранив базу:

```powershell
docker compose down
```

После этого проект можно снова запустить командой `docker compose up --build -d`.

Полный локальный сброс, включая данные PostgreSQL:

```powershell
docker compose down -v
docker compose up --build -d
```

Команда `down -v` удаляет Docker volume с локальной базой. Выполняйте её только если демонстрационные данные больше не нужны.

## 7. Частые проблемы

### `docker compose up` говорит, что сервис завершился с ошибкой

Посмотрите логи конкретного сервиса и общий статус:

```powershell
docker compose ps -a
docker compose logs --tail 200 sync
```

Для другого упавшего сервиса замените `sync` его именем. Не удаляйте volume сразу: журнал обычно показывает исходную причину.

### Docker сообщает о недоступности Engine или daemon

Запустите Docker Desktop, дождитесь **Engine running** и повторите `docker compose ps`. Команда `docker version` должна показывать Client и Server.

### Порт занят

Остановите программу, которая уже использует нужный порт, или измените левую часть соответствующей записи `ports` в `docker-compose.yml`. Пересоздайте сервис после изменения.

### Веб-панель не открывается или пишет об отсутствии соединения

Убедитесь, что `frontend` и `api` запущены, затем обновите страницу. Проверьте `docker compose logs --tail 200 frontend api`. После свежей сборки можно выполнить `docker compose up --build -d frontend api`.

### Фоновые сервисы не обрабатывают заявку

Проверьте, что `sync` завершился как `Exited (0)`, а `worker`, `stream-producer`, `dispatcher` и `ais-emulator` работают. Затем просмотрите их логи командой из раздела 5.

## 8. Архитектура и API

Внешняя АИС отправляет событие в webhook балансировщика. Обработчик проверяет секрет и идентификатор события; база данных хранит заявку, правила, исполнителей и transactional outbox. Producer публикует события в Redis Streams, consumer group передаёт их worker-процессам, а dispatcher доставляет результат эмулятору АИС. Подтверждение возвращается отдельным webhook. Операции, влияющие на лимиты, защищены транзакциями и блокировками.

Swagger со всеми доступными маршрутами и схемами запросов находится на http://localhost:8000/docs. Ключ API задаётся переменной `API_KEY`; секрет webhook — `WEBHOOK_SECRET`. Дополнительные схемы и технические решения приведены в каталоге `docs/`.

